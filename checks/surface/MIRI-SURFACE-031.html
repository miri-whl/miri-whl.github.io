MIRI-SURFACE-031 — Orders entries stably across repeated requests

Orders entries stably across repeated requests

must severity LOW · 1 weight 2 Discovery Contract

Definition: standards/consumption/checks/MIRI-SURFACE-031.yaml · view · raw

Violation
api-index(...) called twice -> entries in dict-insertion order, differing between the two calls
Compliant
api-index(...) called twice -> identical code-point ordering by entry key both times

Why this matters

Without a stable order, "the first 25" is a different 25 per call and truncation is unreproducible — a conformance check written against a padded index becomes flaky rather than wrong, and a consumer that pages through a listing silently sees some entries twice and others never. Locale collation is the common cause — it varies by machine, so two consumers of one surface disagree about what page two contains.

Definition

Surface obligation from the Discovery Contract (3.5.1). This check verifies one property only: that every listing operation returns entries in the ordering 3.5.1 assigns it, ascending by Unicode code point over the NFC-normalized key, and that the ordering is identical across identical requests. Cursor continuation is a separate obligation scored by MIRI-SURFACE-033, because a surface can order perfectly and continue not at all, and a single check covering both cannot say which failed.

When it fires

  • Two identical requests return the same entries in different orders
  • Entries are ordered by locale collation rather than Unicode code point
  • A listing operation orders by a key other than the one 3.5.1 assigns it

How to fix it

Order by Unicode code point over the operation's assigned key, stably across identical requests

  1. Order entries ascending by Unicode code point over the NFC-normalized key named for that operation in 3.5.1
  2. Keep the ordering independent of dict insertion, locale, and process
