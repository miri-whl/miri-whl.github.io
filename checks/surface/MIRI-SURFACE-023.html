MIRI-SURFACE-023 — Fetches nothing

Fetches nothing: never resolves a URL found in a served document

must severity CRITICAL · 5 weight 3 Discovery ContractLifecycle and Security Metadata §9.2

Definition: standards/consumption/checks/MIRI-SURFACE-023.yaml · view · raw

Violation
requests.get(doc["update_check"]["url"]) # to annotate the response with "latest version"
Compliant
{"schema_version": "1", "ok": true, "present": true, "document": {"update_check": {"url": "http://169.254.169.254/…"}}} # relayed verbatim, never dereferenced

Why this matters

A surface that resolves a publisher-declared URL turns publisher-controlled data into server-side requests — the SSRF exposure the producer standard guards, relocated into the query surface itself. The adversarial fixture points update_check.url at the cloud-metadata address precisely so this is testable: a conformant surface serves that value unchanged and never dereferences it. Separating it from import-freedom matters because the two are caught by different fixtures — an import canary cannot detect a fetch.

Definition

Surface obligation from the Discovery Contract §9.2. Split from MIRI-SURFACE-022 in 0.3-draft: import-free discovery and fetch-nothing are different prohibitions with different failure modes and different evidence, and bundling them meant a surface failing only one still failed a check that could not say which.

When it fires

  • The surface resolves, fetches, or issues any network request to a URL appearing in or derived from a served document
  • The surface enriches, annotates, or validates a response using the result of such a request
  • An advisory or update-check endpoint is contacted while answering any §3 operation

How to fix it

Serve declared URLs as opaque strings; resolving them is the consumer's act under the §9.2 guard

  1. Serve declared URLs as opaque strings; resolving them is the consumer's act under the §9.2 guard
  2. Assert in tests that answering every operation issues no outbound connection
