MIRI-CLI-033 — Teaching errors

Invoking a removed surface yields the structured error (code, retryable: false, suggestions) — not a generic parse failure

must severity HIGH · 4 weight 4 conditional requires previous-release CLI Spec §6/§6.3-4

Definition: standards/cli/checks/MIRI-CLI-033.yaml · view · raw

Violation
$ acme-cli get --export Error: unknown flag: --export Usage: acme-cli get [flags] # dead end: nothing names --output archive; a stale agent retries blind
Compliant
$ acme-cli get --export {"schema_version": "1", "ok": false, "error": {"code": "FLAG_REMOVED", "flag": "--export", "removed_in": "1.18.0", "retryable": false, "suggestions": ["use --output archive instead"]}}

Why this matters

When kubectl v1.18 removed get --export, invocations answered with a bare unknown-flag parse error — a dead end that broke Helm template generation and backup pipelines with nothing pointing at the successor. For an agent working from stale weights, the dead end triggers the blind-retry loop of landscape §3.1: hallucinated variants, an eventual silent workaround, and no bug report ever filed. The structured tombstone — stable code, retryable: false, non-empty suggestions — converts that permanent failure into a one-turn recovery, which is why it is the single highest-value behavior for frozen-weights consumers.

Definition

Deprecation markers, the changelog, and actual removals must agree; a removed flag that answers with a dead-end error strands every consumer working from stale knowledge. This check verifies: Invoking a removed surface yields the structured error (code, retryable: false, suggestions) — not a generic parse failure.

When it fires

  • for a surface present in the previous release's --describe but absent from the current one, invoking it yields a generic parse failure (usage dump, "unrecognized arguments", "unknown flag") instead of a JSON error on the machine channel
  • the error emitted lacks a stable error.code, retryable: false, or a non-empty suggestions array naming the replacement

How to fix it

Serve the structured teaching error: code, retryable false, suggestions.

  1. Keep removed surfaces registered in the schema-as-data source as tombstones (status: "removed") rather than deleting their entries, so the parser still recognizes them
  2. Route tombstone hits to the §6 structured error: {"schema_version": "1", "ok": false, "error": {"code": "FLAG_REMOVED", "flag": ..., "removed_in": ..., "retryable": false, "suggestions": [...]}}
  3. Derive suggestions from the tombstone's lifecycle.replacement field so the guidance cannot drift from the surface that actually exists (§6.3-3)
  4. Add the §6.3-4 verification to release CI: invoke every surface removed since the prior release and assert the structured error, not a usage dump
