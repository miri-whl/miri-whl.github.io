MIRI-CLI-018 — Wire schema versioned

Top-level schema_version is independent of the release version

must severity MEDIUM · 3 weight 1 CLI Spec §3.1

Definition: standards/cli/checks/MIRI-CLI-018.yaml · view · raw

Violation
{"schema_version": "3.4.1", "identity": {"version": "3.4.1"}} # the contract version is the release number restated; pins are meaningless
Compliant
{"schema_version": "1", "identity": {"version": "3.4.1"}} # payload contract unchanged across the 3.x series; a breaking change would make it "2"

Why this matters

The wire schema and the product move on different clocks: Docker's agent CLI stamps "schema_version": "1" on every payload precisely so the product can reach 2.0 without the contract moving, and Terry Li's envelope pattern versions the envelope because the envelope shape is the API (landscape §2.3, §3.3-1). A schema_version that merely mirrors the release version destroys the signal in both directions: a consumer pinning it must either treat every routine release as a contract break or learn nothing when the payload genuinely breaks mid-series. Per CLI Spec §3.1, schema_version is a top-level field, not nested in identity; MIRI-CLI-010 verifies its presence, this check verifies its independence.

Definition

A CLI must be able to say who it is and what it offers, so scanners can join it against advisory databases and agents can trust the surface they see. This check verifies: the top-level schema_version is a genuine wire-contract version, not a restatement of the release version.

When it fires

  • The top-level schema_version in --describe is identical to identity.version and moves in lockstep with releases
  • No documented policy states which changes bump the top-level schema_version

How to fix it

Version the wire schema separately from the release version and declare it top-level.

  1. Declare a small independent contract version (e.g. "1") as the top-level schema_version, separate from the release version in identity.version, and stamp the same value on every JSON payload (MIRI-CLI-010)
  2. Document the bump policy: it increments only on breaking payload changes — removed or renamed fields, changed types or semantics — never on releases that leave the shape intact
  3. Record each bump as a wire-schema change in changelog --since output (§5.2), and consider serving prior shapes via --schema-version pinning (landscape §3.3-6)
