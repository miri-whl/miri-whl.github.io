MIRI-CLI-024 — Composition legible

Standalone binary carries embedded module info or references a release SBOM

must severity HIGH · 4 weight 3 conditional CLI Spec §3.1/§7.1CycloneDXSPDX

Definition: standards/cli/checks/MIRI-CLI-024.yaml · view · raw

Violation
Release v3.2.0 assets: acme-cli-linux-amd64 # stripped Rust binary, no .dep-v0 section checksums.txt --describe identity: {"purl": "pkg:generic/acme/acme-cli@3.2.0"} # no "sbom" key $ trivy rootfs . # 0 packages found — the vendored OpenSSL is invisible
Compliant
Release v3.2.0 assets: acme-cli-linux-amd64 # built with cargo auditable build --release sbom.cdx.json # CycloneDX, 214 components --describe identity: "sbom": "https://releases.acme.example/acme-cli/3.2.0/sbom.cdx.json", "build_info": {"embedded_modules": true}

Why this matters

Only the Go toolchain makes binaries legible by default — the embedded module list behind go version -m is what govulncheck, Trivy, and osv-scanner read. Every other standalone binary falls into CPE-guessing territory, where vendor/product strings are inferred from file names and cve-bin-tool resorts to byte-signature detection of roughly 400 known components; a stripped binary with no SBOM reference can carry a statically linked OpenSSL with last month's CVE through every scanner in the pipeline unnoticed. cargo auditable shows the fix is cheap: a zlib-compressed JSON dependency list in a .dep-v0 linker section, under 4 kB, already consumed by cargo-audit (≥0.17.3), Trivy (≥0.31.0), and osv-scanner (≥2.0.1).

Definition

A CLI must be able to say who it is and what it offers, so scanners can join it against advisory databases and agents can trust the surface they see. This check verifies: Standalone binary carries embedded module info or references a release SBOM.

When it fires

  • identity.purl indicates direct binary distribution (pkg:generic/ with repository_url) — registry-distributed CLIs pass this conditional check automatically
  • the binary yields no embedded module inventory (go version -m fails, no .dep-v0 section) and build_info.embedded_modules is absent or false
  • identity.sbom is absent, or the referenced URL/path does not resolve to a CycloneDX/SPDX document for the release under test

How to fix it

Publish a CycloneDX/SPDX SBOM per release (or use cargo auditable / Go buildinfo).

  1. Generate a per-release SBOM in the release pipeline (syft <binary> -o cyclonedx-json > sbom.cdx.json, or ecosystem-native tools such as cyclonedx-gomod / cargo cyclonedx) and publish it next to the release artifacts (§7.1)
  2. Reference it from identity.sbom in the --describe output
  3. On Go, keep the default buildinfo embedding and set build_info.embedded_modules: true; on Rust, build with cargo auditable build --release
  4. Verify legibility as a scanner would: osv-scanner scan <binary> or trivy rootfs <dir> must report the dependency tree
