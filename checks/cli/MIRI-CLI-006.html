MIRI-CLI-006 — Non-interactive default

No command blocks on a prompt when stdin is not a TTY

must severity CRITICAL · 5 weight 3 CLI Spec §2.5anc.dev

Definition: standards/cli/checks/MIRI-CLI-006.yaml · view · raw

Violation
$ tool init </dev/null This will create 3 resources. Continue? [y/N] (process blocks on read; the CI job burns 60 minutes and dies with a timeout that never mentions the prompt)
Compliant
$ tool init </dev/null (stderr) confirmation required and stdin is not a TTY (stdout) {"schema_version": "1", "ok": false, "error": {"code": "CONFIRMATION_REQUIRED", "retryable": false, "suggestions": ["re-run with --yes"]}} $ echo $? 1 # immediate, structured, recoverable in one turn

Why this matters

A tool that prompts when stdin is not a TTY hangs silently: the agent never sees a question, only a stall that ends when the harness or CI timeout kills the job — and the timeout error says nothing about the prompt that caused it. This failure class recurs in shipped tools: pnpm dlx hangs CI jobs on its build-scripts approval prompt (pnpm/pnpm#12108), and opennextjs-cloudflare build blocks non-TTY builds on a config prompt (opennextjs-cloudflare#1198). Failing fast with a structured error naming the answering flag converts an unbounded hang into a one-turn recovery, which is why this check is CRITICAL.

Definition

Agents drive CLIs through the same conventions humans and scripts rely on; a tool that breaks them is invisible or hangs silently in a non-interactive context. This check verifies: No command blocks on a prompt when stdin is not a TTY.

When it fires

  • With stdin closed (</dev/null), any command prints a prompt and blocks on a read from stdin instead of exiting
  • Any command blocks awaiting input in a non-TTY context without printing anything at all
  • A confirmation exists that has no flag or environment equivalent recorded in --describe

How to fix it

Never prompt when stdin is not a TTY; fail fast or take flags.

  1. Detect !isatty(stdin) and never prompt in that state — this must be the default, not opt-in via a --non-interactive flag
  2. Where confirmation is required, fail fast with a structured error naming the answering flag, e.g. {"schema_version": "1", "ok": false, "error": {"code": "CONFIRMATION_REQUIRED", "retryable": false, "suggestions": ["re-run with --yes"]}} (CLI Spec §2.6)
  3. Give every prompt a flag or environment equivalent (--yes, --strategy <v>) and record it in --describe
  4. Add a CI matrix running every command with </dev/null under a short timeout; any timeout expiry is a failure of this check
