MIRI-CLI-029 — changelog --since

changelog --since <v> --json implemented

must severity HIGH · 4 weight 4 CLI Spec §5.2

Definition: standards/cli/checks/MIRI-CLI-029.yaml · view · raw

Violation
$ acme-cli changelog --since 3.0.0 --json Error: unknown command "changelog" for "acme-cli" # the only changelog is prose on the forge — nothing a returning agent can query
Compliant
$ acme-cli changelog --since 3.0.0 --json {"schema_version": "1", "releases": [ {"version": "3.1.0", "added": ["--output archive"], "deprecated": [{"surface": "--export", "removed_in": "3.2.0", "replacement": "--output archive"}]}, {"version": "3.2.0", "removed": ["--export"]}]}

Why this matters

check-update says only *that* the tool moved; changelog --since says *what* moved. It is the recovery primitive for consumers whose knowledge froze at an older release — frozen weights can never read release notes, and a skill file is only as fresh as its last regeneration (landscape §3.1). Without it, an agent returning after three releases rediscovers surface changes by trial and error: construct from stale knowledge, hit an error, retry with hallucinated variants — the silent degradation loop in which no bug report is ever filed.

Definition

An agent that has been away for three releases must be able to ask what moved; update state must be queryable, passive, and honest offline. This check verifies: changelog --since <v> --json implemented.

When it fires

  • no changelog subcommand exists, or changelog --since <v> --json exits non-zero for a version that exists in the published release history
  • --since rejects valid prior versions or ignores the bound and dumps the full history
  • output is not a JSON document on stdout grouped per release between <v> and the current version

How to fix it

Implement changelog --since <version> --json per CLI Spec §5.2.

  1. Implement changelog --since <version> --json per §5.2, emitting one entry per release between <version> and current
  2. Derive it from the same schema-as-data struct that generates --help and --describe (§2.3) — a mechanical diff of the schema between releases, never hand-written notes
  3. Validate accepted --since values against the same release manifest check-update consults, so every published version is accepted
