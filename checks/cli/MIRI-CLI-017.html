MIRI-CLI-017 — Version coherence

identity.version equals the binary's actual --version

must severity HIGH · 4 weight 2 CLI Spec §9-1

Definition: standards/cli/checks/MIRI-CLI-017.yaml · view · raw

Violation
$ acme --version 3.4.0 $ acme --describe | jq -r .identity.version 3.2.0 # a scanner judges 3.2.0's advisories against a binary that is 3.4.0
Compliant
$ acme --version 3.4.0 $ acme --describe | jq -r '.identity.version, .identity.purl' 3.4.0 pkg:npm/acme-cli@3.4.0

Why this matters

The usual drift mechanism is two version sources: --version stamped at build time (a git tag injected via -ldflags) while --describe carries a hard-coded constant nobody bumps, or the reverse. Once they disagree, the tool's two identity surfaces contradict each other with no way to tell which is lying — and the consumers diverge: scanners compute vulnerability verdicts from --describe's version while humans and scripts read --version, so a fix can look applied on one surface and absent on the other. Spec §9-1 makes agreement, including the purl's version segment, a conformance requirement.

Definition

A CLI must be able to say who it is and what it offers, so scanners can join it against advisory databases and agents can trust the surface they see. This check verifies: identity.version equals the binary's actual --version.

When it fires

  • The version printed by --version differs from identity.version in --describe
  • The @version segment of identity.purl differs from identity.version

How to fix it

Derive both from the single version source in the build.

  1. Keep exactly one version constant, injected at build time (go build -ldflags "-X main.version=$TAG"; the package.json version field; importlib.metadata.version() in Python)
  2. Derive --version, identity.version, and the purl's @version segment from that constant
  3. Add a CI gate: [ "$(acme --version)" = "$(acme --describe | jq -r .identity.version)" ]
