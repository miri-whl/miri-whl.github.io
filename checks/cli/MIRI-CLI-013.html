MIRI-CLI-013 — Structured errors

Failures emit JSON with a stable machine error.code

must severity HIGH · 4 weight 3 CLI Spec §6

Definition: standards/cli/checks/MIRI-CLI-013.yaml · view · raw

Violation
$ acme deploy --export Error: unrecognized arguments: --export $ echo $? 2 # prose only; nothing an agent can branch on survives a rewording
Compliant
$ acme deploy --export {"schema_version": "1", "ok": false, "error": {"code": "FLAG_REMOVED", "flag": "--export", "removed_in": "1.18.0", "retryable": false, "suggestions": ["use --output archive instead"]}}

Why this matters

CLI Spec §6 makes the machine code the one stable surface of a failure: prose wording is free to change between releases, so an agent that branches on message text breaks silently the first time a sentence is reworded. The precedent is settled API practice — AWS service errors carry machine codes such as ThrottlingException that SDK retry classifiers branch on, and RFC 9457 separates the stable problem type from the human detail field consumers are told not to parse. A failure that emits only prose and a bare non-zero exit is the dead end of landscape §3.3: the agent retries with hallucinated variants until something works, and no bug report is ever filed.

Definition

Agents parse stdout; anything unstructured, inconsistent, or polluted forces guesswork and burns recovery turns. This check verifies: Failures emit JSON with a stable machine error.code.

When it fires

  • A documented-typed argument given a value outside its type (an unparseable version for --since, a path that cannot exist, a value outside an enumerated set) is accepted and reported as success rather than answered with VALIDATION — the check's other clauses all presuppose a failure, so without this one a CLI that never rejects anything passes by never failing, and its callers cannot tell a real answer from a silently coerced one
  • An induced failure exits non-zero with prose only — no JSON error payload on the machine channel
  • The error payload lacks error.code, or lacks ok: false, on a failing invocation
  • Error codes appear nowhere in the documented wire contract, leaving message text as the only branching surface
  • The same induced failure yields an error.code different from the documented one

How to fix it

Emit structured errors with a stable machine error.code.

  1. Emit {"schema_version": "1", "ok": false, "error": {"code": ...}} as JSON on the machine channel for every failure path, per CLI Spec §6
  2. Assign UPPER_SNAKE codes from a closed, documented set (AUTH_EXPIRED, FLAG_REMOVED, RESOURCE_NOT_FOUND) and treat the set as API: codes are added, never repurposed or renumbered
  3. Keep the human explanation in a separate message field that may change freely; keep warnings on stderr so they never corrupt the payload (§2.5)
  4. Route removed-surface invocations through the structured FLAG_REMOVED teaching error of §6 rather than the argument parser's generic failure
