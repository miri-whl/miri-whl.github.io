MIRI-CLI-016 — Identity purl

identity.purl present, well-formed, matches distribution channel

must severity CRITICAL · 5 weight 3 CLI Spec §3.1purl spec

Definition: standards/cli/checks/MIRI-CLI-016.yaml · view · raw

Violation
"identity": {"version": "3.2.0", "distribution": "open-source"} # no purl: scanners are back to guessing a CPE from the binary's file name
Compliant
"identity": {"purl": "pkg:brew/acme-cli@3.2.0", "version": "3.2.0"} # matches the Homebrew channel; joins directly against OSV records for that name

Why this matters

Every scanner runs the same loop — build inventory, normalize to purl, compare against OSV affected ranges — so the purl is the single join key that makes vulnerability and currency verdicts computable; a CLI without one falls back to CPE matching, where vendor/product strings must be guessed from binary names and internal tools are simply invisible. The type must match the distribution channel because advisory records attach to registry-native names: a Homebrew-distributed tool declaring pkg:generic never joins against records filed under its brew coordinates. Spec §3.1 therefore requires the channel's own purl type (pkg:npm, pkg:pypi, pkg:cargo, pkg:brew, …), reserving pkg:generic with a repository_url qualifier for direct binary distribution.

Definition

A CLI must be able to say who it is and what it offers, so scanners can join it against advisory databases and agents can trust the surface they see. This check verifies: identity.purl present, well-formed, matches distribution channel.

When it fires

  • identity.purl is absent from the --describe output
  • The value fails purl grammar — no pkg: scheme, missing type or name, or no @version segment
  • The purl type contradicts the actual install channel (an npm-distributed tool declaring pkg:generic; a Homebrew formula declaring pkg:npm)
  • The type is pkg:generic without a repository_url qualifier locating the release source

How to fix it

Declare identity.purl using the distribution channel's purl type.

  1. Choose the purl type of the real distribution channel: pkg:npm/, pkg:pypi/, pkg:cargo/, pkg:golang/, pkg:brew/; use pkg:generic/<org>/<name>@<version>?repository_url=<releases URL> only for direct binary distribution
  2. Embed the purl at build time from the release version (e.g. go build -ldflags "-X main.purl=pkg:brew/acme-cli@$VERSION") so it cannot drift from the artifact
  3. Validate the value in CI with a purl library (packageurl-python, packageurl-go) before publishing
