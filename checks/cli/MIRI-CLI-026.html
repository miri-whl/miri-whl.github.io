MIRI-CLI-026 — Passive by default

No implicit update check on normal invocations; nothing printed to other commands' stdout

must severity MEDIUM · 3 weight 2 CLI Spec §5.1

Definition: standards/cli/checks/MIRI-CLI-026.yaml · view · raw

Violation
$ acme-cli list --json | jq . parse error: Invalid literal at line 1, column 9 # stdout began: Update available 3.2.0 -> 3.4.1 Run brew upgrade acme-cli # packet capture shows a connection to releases.acme.example during list
Compliant
$ acme-cli list --json # sandboxed: zero network calls, clean payload {"schema_version": "1", "items": ["alpha", "beta"]} $ acme-cli check-update --json # the only command that touches the manifest

Why this matters

update-notifier's default is the cautionary pattern: ordinary invocations spawn an unref'd child that phones the npm registry on a daily interval, with opt-out left to the loose NO_UPDATE_NOTIFIER convention — a phone-home the user never requested and cannot discover from --help. Worse than the privacy leak is channel corruption: an "update available" banner printed to stdout lands inside the JSON payload and every downstream parser fails simultaneously (§2.5). §5.1 therefore makes the check passive: update state is consulted only when check-update is explicitly invoked.

Definition

An agent that has been away for three releases must be able to ask what moved; update state must be queryable, passive, and honest offline. This check verifies: No implicit update check on normal invocations; nothing printed to other commands' stdout.

When it fires

  • an ordinary command (e.g. <cli> list --json) issues network requests to a release manifest, registry, or notifier endpoint
  • update or upgrade text appears on the stdout of any command other than check-update, or on stderr of ordinary commands in non-interactive contexts
  • update-check cache or interval-timestamp files change after invocations that were not check-update

How to fix it

Make update checks passive: only on explicit check-update.

  1. Remove implicit update polling from command startup; confine manifest access to explicit check-update invocations
  2. If an interactive hint is retained, gate it on stderr being a TTY and write it to stderr only — never stdout, never in non-interactive contexts
  3. Drop homegrown opt-out switches (NO_UPDATE_NOTIFIER-style) once the default is passive; there is nothing left to opt out of
  4. Add a CI test that runs ordinary commands under blocked egress and asserts zero update-related connections and byte-identical stdout
