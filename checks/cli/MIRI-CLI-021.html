MIRI-CLI-021 — EOL coherence

support.status deprecated/eol ⇒ replacement present

must severity HIGH · 4 weight 2 CLI Spec §3.2

Definition: standards/cli/checks/MIRI-CLI-021.yaml · view · raw

Violation
"support": {"status": "eol", "replacement": null} # every caller is told the tool is dead and nothing else
Compliant
"support": {"status": "deprecated", "eol_date": "2027-01-31", "replacement": "pkg:generic/acme/acme-cli2"}

Why this matters

Spec §3.2 requires replacement whenever status is deprecated or eol, because a deprecation without a successor tells consumers only to leave, with no destination — the workflow the tool served still exists, and every consumer must rediscover where it went. The rule follows the converged deprecation vocabulary in which the marker always carries the forward path (PEP 702's @deprecated message, Rust's #[deprecated(note)], RFC 9745's deprecation link relation), delivered here through --describe — the one channel that reaches frozen-weights consumers at call time. lifecycle-v1.json encodes the same constraint as a conditional requirement.

Definition

A CLI must be able to say who it is and what it offers, so scanners can join it against advisory databases and agents can trust the surface they see. This check verifies: support.status deprecated/eol ⇒ replacement present.

When it fires

  • support.status is "deprecated" or "eol" while support.replacement is null or absent
  • replacement is present but is neither a well-formed purl nor a subcommand path in an absorbing CLI

How to fix it

Name the successor (purl or absorbing subcommand).

  1. Name the successor tool as a purl: "replacement": "pkg:generic/acme/acme-cli2"
  2. When the successor is absorption into another CLI, name the subcommand path instead (e.g. "acme2 legacy deploy")
  3. Set eol_date alongside, and publish a migration guide so the per-flag lifecycle blocks (§6) can point individual surface moves at it
