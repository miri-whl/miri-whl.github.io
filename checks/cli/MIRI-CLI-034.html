MIRI-CLI-034 — Warnings on stderr

Grace-period deprecation warnings never touch stdout

must severity MEDIUM · 3 weight 2 conditional CLI Spec §2.5

Definition: standards/cli/checks/MIRI-CLI-034.yaml · view · raw

Violation
$ tool export --json > out.json $ cat out.json WARNING: --export is deprecated, use --output archive {"ok": true, "schema_version": "1", ...} $ jq . out.json jq: error (at out.json:1): Invalid literal — every downstream parser fails at once
Compliant
$ tool export --json 1>out.json 2>err.txt $ cat err.txt warning: --export deprecated since 1.14.0, removed in 1.18.0; use --output archive $ jq -e .ok out.json true — the payload parses clean, the warning reached the diagnostic channel

Why this matters

Spec §2.5 confines machine payloads to stdout and all deprecation and update warnings to stderr, because the two channels have different consumers: stdout feeds a parser, stderr feeds a diagnostician. A warning line prepended to a JSON payload fails every downstream json.loads and jq invocation simultaneously — and it fails precisely for the consumers who just invoked the deprecated surface, the ones the warning was written to migrate. The grace period of §7.3 only works if the deprecated surface keeps functioning, and a corrupted payload means it does not.

Definition

Deprecation markers, the changelog, and actual removals must agree; a removed flag that answers with a dead-end error strands every consumer working from stale knowledge. This check verifies: Grace-period deprecation warnings never touch stdout.

When it fires

  • Invoking a surface whose lifecycle.status is deprecated emits no deprecation warning on **either** channel — the grace period exists so that a caller is told before removal, and a tool that warns nowhere satisfies every clause about *which channel* the warning avoids by never emitting one
  • Invoking a surface whose lifecycle.status is deprecated with the JSON output flag produces stdout that is not a single parseable JSON document
  • Deprecation notice text (e.g. a line matching /deprecat/i naming the surface) appears in captured stdout rather than in captured stderr
  • Warning output interleaves with or prefixes the payload only when the deprecated surface is used — the clean-payload check (MIRI-CLI-011) passes on non-deprecated invocations of the same command

How to fix it

Emit grace-period warnings on stderr only.

  1. Route all warning emission through a diagnostics writer bound to stderr (fprintf(stderr, ...), Rust eprintln!, Python print(..., file=sys.stderr) — Python's warnings module already defaults there)
  2. Derive the warning text from the surface's lifecycle block per §2.3 so the message, --describe, and changelog --since cannot disagree
  3. Add a pipeline test to CI: cli <cmd> --deprecated-flag --json 1>out.json 2>err.txt && jq -e . out.json && grep -qi deprecated err.txt
