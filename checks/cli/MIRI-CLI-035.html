MIRI-CLI-035 — Grace period

Deprecated surfaces function for ≥1 minor release before removal

must severity HIGH · 4 weight 3 requires previous-release CLI Spec §7.3K8s deprecation policy

Definition: standards/cli/checks/MIRI-CLI-035.yaml · view · raw

Violation
release 2.3.0 --describe: {"name": "--legacy-auth", "lifecycle": {"status": "deprecated", "deprecated_since": "2.3.0"}} $ tool login --legacy-auth # same release 2.3.0 {"ok": false, "error": {"code": "FLAG_REMOVED"}} — announced and dead in the same release; no consumer could have observed the warning while the flag still worked
Compliant
1.14.0: --export marked deprecated, functions, warns on stderr 1.15.0–1.17.x: --export still functions, lifecycle block carries removed_in: "1.18.0" 1.18.0: --export removed; invoking it returns the structured FLAG_REMOVED teaching error

Why this matters

Spec §7.3 requires at least one minor release in which the deprecated surface still functions while warning on stderr and carrying its lifecycle block, following the Kubernetes deprecation policy — the only shipped CLI-specific policy, whose rules 5a/5b require deprecated GA CLI elements of admin-facing components to keep functioning for 6 months or 1 release and of user-facing components for 12 months or 2 releases. The floor exists because an agent CLI's consumers sync on release cadence: skill files regenerated per release, vendored --describe snapshots, pinned automations all need one release in which the old surface works while announcing its end. kubectl get --export had a four-release runway (deprecated 1.14, removed 1.18) and its removal still broke Helm chart generation and CI backup pipelines — one minor release is the minimum, not a comfortable target.

Definition

Deprecation markers, the changelog, and actual removals must agree; a removed flag that answers with a dead-end error strands every consumer working from stale knowledge. This check verifies: Deprecated surfaces function for ≥1 minor release before removal.

When it fires

  • Diffing the previous release's --describe against the current one: a surface removed in this release never appeared with lifecycle.status: deprecated in a release where it still functioned
  • A lifecycle block declares removed_in in the same minor series as deprecated_since
  • changelog --since shows the same surface entering deprecated and removed within one release entry

How to fix it

Keep deprecated surfaces functioning for at least one minor release.

  1. Set removed_in at least one minor release after deprecated_since in the surface's lifecycle block, and publish both fields in the deprecating release
  2. Keep the surface fully functional during the window, emitting the stderr warning of §7.3 on each use
  3. Gate releases in CI: parse the previous release's --describe (obtained via check-update's manifest), and fail if any surface it lists is absent from the current build without an intervening deprecated-and-functioning release
