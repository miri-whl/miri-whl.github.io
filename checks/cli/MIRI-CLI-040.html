MIRI-CLI-040 — Danger marked

Destructive operations flagged as such in --describe

must severity HIGH · 4 weight 3 CLI Spec §6.4Landscape §2.1 P16

Definition: standards/cli/checks/MIRI-CLI-040.yaml · view · raw

Violation
--describe: {"name": "purge", "description": "Remove all cached artifacts", "mutating": true} Nothing distinguishes purge from an ordinary write; an agent's guardrail layer has no field to branch on and invokes it like any other command.
Compliant
--describe: {"name": "purge", "description": "Remove all cached artifacts", "mutating": true, "destructive": true} $ tool purge {"schema_version": "1", "ok": false, "error": {"code": "CONFIRMATION_REQUIRED", "retryable": false, "suggestions": ["re-run with --force, or preview with --dry-run"]}}

Why this matters

An agent cannot weigh a risk it cannot see: a purge whose --describe entry is indistinguishable from a tag gets retried and parallelized with ordinary-write caution. Agent-First CLI principle 16 (signal danger — guardrails over good luck) and desk's --capabilities output, which enumerates per service which commands are destructive, exist so that a policy layer is possible at all — a harness can require human confirmation or a dry run before destructive calls only if destructiveness is machine-readable rather than implied by prose or a verb name.

Definition

Agents retry, parallelize, and act without human review between steps; mutations must be previewable, marked, and safe to repeat. This check verifies: Destructive operations flagged as such in --describe.

When it fires

  • A command that irrecoverably deletes or overwrites data carries no structured destructive marking (e.g. destructive: true) in its --describe entry
  • Destructiveness is stated only in human help prose, with no field a harness can branch on
  • Commands whose observed behavior destroys data (fixture-based evidence) or whose names conventionally signal it (purge, destroy, reset, rm) are unmarked while other commands in the same binary are marked

How to fix it

Mark destructive operations in the introspection output.

  1. Add destructive: true to the command's schema-as-data definition so --describe and --help both derive it (§2.3)
  2. Require an explicit --force (or --yes) for marked commands when stdin is not a TTY, exiting with a structured CONFIRMATION_REQUIRED error otherwise
  3. Audit the full surface for destruction paths — delete, purge, destroy, reset, and any overwrite of user data — and mark each, pairing the marking with --dry-run support (MIRI-CLI-039)
