MIRI-PY-041 — changelog.json valid

Present for any non-initial release; validates against changelog-v1.json (*conditional*)

must severity HIGH · 4 weight 3 conditional Agent Metadata §4.7schema

Definition: standards/python/checks/MIRI-PY-041.yaml · view · raw

Violation
Wheel 1.2.0 agent-metadata/: sdk-manifest.json usage-patterns.json migration-guide.json lifecycle.json # 1.1.0 exists on the index; no changelog.json — what 1.2.0 fixed is unrecorded
Compliant
agent-metadata/changelog.json: {"schema_version": "1", "releases": [ {"version": "1.2.0", "fixed": [{"summary": "Timeout ignored under TLS", "refs": ["#408"]}]}, {"version": "1.1.0", "added": [{"summary": "Batch fetch", "symbols": ["Client.batch"]}]}]}

Why this matters

The wheel metadata set records breaking changes in migration-guide.json and, until 0.6.0, had no home for what was fixed. The originating incident: a maintainer shipped bug fixes with a silent changelog, and the downstream project that had reported those bugs installed the fix and never learned it — every shipped document was present, schema-valid and stamped in the build window, so no existing check could see it. Agent Metadata §4.7 defines the document; this check is its presence and shape, and MIRI-PY-042 to 044 are the joins that make it mean something.

Definition

The agent-metadata directory is the wheel's machine-readable surface; every file in it must be present, schema-valid, and generated at build time. This check verifies: changelog.json is present for any non-initial release and validates against changelog-v1.json. Conditional exactly as MIRI-PY-009: a first release has nothing to describe, and requiring the document unconditionally would manufacture the empty-artifact class the freshness contract exists to kill.

When it fires

  • A previous release exists (the linter can establish one — MIRI-PY-030's condition) and agent-metadata/changelog.json is absent from the wheel
  • The document is present and fails validation against changelog-v1.json — schema_version not "1", releases empty, an entry without summary, an unknown key anywhere
  • releases is not ordered newest-first by PEP 440 version

How to fix it

Generate changelog.json from change fragments at build time; validate against changelog-v1.json.

  1. Assemble changelog.json at build time from per-change fragments (towncrier-class tooling): a change lands with a fragment or CI fails, and the release assembles the document
  2. Validate before packaging: check-jsonschema --schemafile changelog-v1.json src/example_sdk/agent-metadata/changelog.json
  3. Keep deprecated and removed entries in agreement with migration-guide.json; it remains the authoritative lifecycle record
