MIRI-PY-004 — Declarative build config

pyproject.toml with [project] table drives the build

should severity MINOR · 2 weight 2 PEP 621PEP 517

Definition: standards/python/checks/MIRI-PY-004.yaml · view · raw

Violation
pyproject.toml: absent setup.py: version = subprocess.check_output(['git', 'describe']).decode() setup(name='example-sdk', version=version, install_requires=open('reqs.txt').read().splitlines()) # nothing here is knowable without executing the file
Compliant
pyproject.toml: [build-system] requires = ["hatchling"] build-backend = "hatchling.build" [project] name = "example-sdk" version = "2.1.0" dependencies = ["httpx>=0.27"]

Why this matters

A setup.py is executed code: the only way to learn the metadata inside it is to run it, which is why static analyzers, index scanners, and Miri's own generators cannot see it — and why sdist installs remain an arbitrary-code-execution point. PEP 621's [project] table makes name, version, dependencies, and entry points readable by parsing one TOML file, the same property the Miri build step relies on to generate agent-metadata/ without importing the package. PEP 517's [build-system] table lets any frontend build the wheel deterministically instead of guessing at a setup.py invocation.

Definition

Miri builds on the existing packaging standards rather than replacing them; a wheel that violates the baseline cannot carry trustworthy agent metadata. This check verifies: pyproject.toml with [project] table drives the build.

When it fires

  • The project ships no pyproject.toml, or pyproject.toml lacks a [project] table
  • Name, version, or dependencies are discoverable only by executing setup.py or reading setup.cfg
  • No [build-system] table declares requires and build-backend
  • [project] marks a field dynamic without a declared tool source that supplies it

How to fix it

Move project metadata to the [project] table of pyproject.toml.

  1. Move name, version, dependencies, optional-dependencies, and entry points into [project] (PEP 621); if the version is computed, declare dynamic = ["version"] backed by setuptools-scm or hatch-vcs rather than code in setup.py
  2. Declare [build-system] with requires and build-backend (PEP 517/518)
  3. Keep setup.py only as an empty setup() shim if a legacy toolchain still requires one
  4. Validate the file in CI with validate-pyproject pyproject.toml
