Compliant
agent-metadata/migration-guide.json: {"from_version": "2.0.x", "to_version": "2.1.0", "migration_type": "minor", "generated_at": "2026-08-01T12:00:00Z", "summary": {"breaking_changes": 1, "new_features": 2, "deprecations": 1}, "deprecations": [{"id": "execute_rename", "deprecated": "Client.execute()", "replacement": "Client.query()", "removal_version": "3.0.0"}]}

Why this matters

A coding agent's knowledge of an API is frozen at its training cutoff, and the effect is measured, not hypothetical: empirical studies of LLM code completion report deprecated-API usage rates of 25-38% across eight popular Python libraries, because the model writes for version N-1 against an installed version N. migration-guide.json is the machine-readable delta that closes this gap at generation time, and per Agent Metadata §4.3 its deprecations MUST be derived from the code's PEP 702 @deprecated markers, so the guide cannot drift from what the interpreter itself warns about. A non-initial release that ships without one strands every frozen-knowledge consumer with no structured path forward.

Definition

The agent-metadata directory is the wheel's machine-readable surface; every file in it must be present, schema-valid, and generated at build time so agents can consume it without parsing or guessing. This check verifies: Present for any non-initial release; validates against schema.

When it fires

  • The wheel is not the project's first release and agent-metadata/migration-guide.json is absent
  • The document fails migration-guide-v1.json validation (any of from_version, to_version, migration_type, generated_at, summary missing)
  • to_version does not equal the wheel's own version, or from_version names no actually published prior release line
  • A deprecations entry lacks id, deprecated, or replacement

How to fix it

Generate migration-guide.json for every non-initial release.

  1. Generate migration-guide.json in the release build, deriving deprecations from PEP 702 markers (warnings.deprecated on Python 3.13+, typing_extensions.deprecated earlier)
  2. Set to_version to the release being built and from_version to the prior supported line (e.g. "2.0.x")
  3. Populate breaking_changes with old_code/new_code pairs, adding automated_fix find/replace patterns where a mechanical rewrite exists
  4. Cover every release line still under support, not only N-1
