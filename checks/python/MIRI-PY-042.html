MIRI-PY-042 — Version silence

changelog.json releases[0].version equals the wheel's version (*conditional*: document present)

must severity HIGH · 4 weight 3 conditional Agent Metadata §4.7

Definition: standards/python/checks/MIRI-PY-042.yaml · view · raw

Violation
METADATA: Version: 1.2.0 changelog.json releases[0].version: "1.1.0" # 1.2.0's fixes are unrecorded; the newest entry is a release old
Compliant
METADATA: Version: 1.2.0 changelog.json releases[0].version: "1.2.0" # the document describes the release it ships in

Why this matters

This single rule would have caught the incident that produced the freshness contract: fixes shipped, changelog untouched, downstream never told. It is the cheapest join in the standard — one string against one string — and it is decidable with nothing but the wheel. Stamp drift (MIRI-PY-011) catches a document generated at the wrong time; version silence catches one generated at the right time about the wrong release, which no timestamp can see.

Definition

Agents working from frozen model weights cannot read changelogs; the machine-readable one must describe the release it ships in. This check verifies: whenever changelog.json ships, its newest entry is the wheel's own version. A changelog whose newest entry describes an earlier release is not thin, it is lying about currency — which is why this check's obligation sits at currency rather than at existence.

When it fires

  • changelog.json is present and releases[0].version, parsed as PEP 440, is not equal to the wheel's version from METADATA
  • releases[0].version does not parse as PEP 440 at all

How to fix it

Make the newest changelog entry the version being built.

  1. Assemble the release's entry at build time from fragments so the newest entry cannot lag the version being built
  2. Fail the build when releases[0].version differs from the version in pyproject.toml / METADATA
