MIRI-PY-025 — SBOM purls resolvable

SBOM component purls are well-formed

should severity MINOR · 2 weight 1 conditional PEP 770purl spec

Definition: standards/python/checks/MIRI-PY-025.yaml · view · raw

Violation
sboms/vendored.cdx.json component: {"name": "openssl", "purl": "openssl 3.1.3"} # not a purl; scanners skip the component — OpenSSL is unscanned again
Compliant
{"name": "openssl", "purl": "pkg:generic/openssl@3.1.3"} # parses; joins against OSV affected ranges and endoflife.date EoL data

Why this matters

SBOM components join against advisory and end-of-life data by purl (§3.2): scanners normalize each component identifier and query with it. A component whose identifier fails purl parsing is not reported as an error — matching tools skip what they cannot normalize — so the component silently drops out of every scan while the SBOM's presence makes the wheel look fully covered. One malformed purl converts MIRI-PY-024's guarantee back into the phantom-dependency gap it exists to close.

Definition

Vulnerability and currency verdicts are computed externally by joining declared identity against advisory databases; a wheel that misdeclares identity or sources silently breaks that join. This check verifies: SBOM component purls are well-formed.

When it fires

  • Any component in a .dist-info/sboms/ document lacks a purl
  • Any component purl fails parsing under the purl specification grammar (pkg: scheme, type, name, optional version and qualifiers)

How to fix it

Emit valid purls for every SBOM component.

  1. Generate purls with a purl library (packageurl-python: PackageURL(type="generic", name="openssl", version="3.1.3").to_string()) rather than string formatting
  2. Add a CI step that round-trips every SBOM component identifier through PackageURL.from_string() and fails the build on a parse error
