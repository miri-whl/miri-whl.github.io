MIRI-PY-032 — Removal versions sane

Every removal_version is greater than the current release

must severity MINOR · 2 weight 2 Lifecycle §6.4-3PEP 440

Definition: standards/python/checks/MIRI-PY-032.yaml · view · raw

Violation
weather-sdk 2.0.0 ships migration-guide.json: {"deprecated": "WeatherClient.legacy_connect()", "replacement": "WeatherClient.connect()", "removal_version": "1.9.0"} # legacy_connect() still exists in 2.0.0 — the metadata claims a removal that never happened
Compliant
weather-sdk 2.0.0 ships migration-guide.json: {"deprecated": "WeatherClient.legacy_connect()", "replacement": "WeatherClient.connect()", "removal_version": "3.0.0"} # 2.0.0 < 3.0.0 under PEP 440 — the interface still shipping is exactly what the schedule predicts

Why this matters

removal_version is the field an agent uses to decide urgency — migrate now, or at the next regeneration cycle. A value at or below the shipping version is self-refuting: the interface demonstrably still exists in a release that claims to postdate its removal, and the consumer cannot tell whether the schedule went stale or the deletion was forgotten, so the whole inventory loses its authority as a schedule. The usual cause is mechanical — the removal plan slips, the version rolls past the promised release, and a hand-maintained field is never touched — which is why Lifecycle §6.2 requires the inventory to be derived from the PEP 702 decorators at build time. Comparison uses PEP 440 ordering, the same total order pip resolves with.

Definition

Agents working from frozen model weights cannot read changelogs; deprecation must be marked in code, inventoried in metadata, and never resolved by silent removal. This check verifies: Every removal_version is greater than the current release.

When it fires

  • A deprecations[].removal_version in migration-guide.json compares less than or equal to the wheel's own version from dist-info/METADATA under PEP 440 ordering (packaging.version.Version)
  • A removal_version does not parse as a valid PEP 440 version at all

How to fix it

Set removal_version to a future release.

  1. Derive removal_version from the @deprecated decorator message at build time (Lifecycle §6.2) so a slipped plan is corrected in one place
  2. When a removal slips, update the decorator to the new target release before cutting the release; regeneration propagates the change to the JSON
  3. Gate the release in CI: compare every removal_version against the version being built with packaging.version.Version and fail on <=
