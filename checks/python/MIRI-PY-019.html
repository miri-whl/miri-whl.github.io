MIRI-PY-019 — purl coherence

identity.purl name+version exactly match METADATA

must severity CRITICAL · 5 weight 4 purl specLifecycle §8 (Conformance Requirements), item 2

Definition: standards/python/checks/MIRI-PY-019.yaml · view · raw

Violation
METADATA: Name: Example_SDK Version: 2.1.1 lifecycle.json: "purl": "pkg:pypi/Example_SDK@2.1.0" <- non-normalized name never matches OSV's key, and the version is one patch behind: every advisory query runs against an artifact this wheel is not
Compliant
METADATA: Name: Example_SDK Version: 2.1.1 lifecycle.json: "purl": "pkg:pypi/example-sdk@2.1.1" (name equals the PEP 503 normalization of METADATA Name; version equals METADATA Version exactly; CI asserts both before upload)

Why this matters

identity.purl is the join key for every advisory lookup (Lifecycle §3.1), and §8 item 2 requires it to match dist-info METADATA name and version exactly; a mismatched purl queries OSV for an artifact the wheel is not, and the clean empty response reads as "not vulnerable". Declared identity diverging from installed identity is also the signature of dependency confusion — the mechanism of Birsan's 2021 research, which reached code execution inside Apple, Microsoft, PayPal, Shopify, and some thirty other companies by publishing internal package names to public registries. Exactness includes PEP 503 normalization: OSV and the index APIs key on the normalized name, so a purl carrying Example_SDK never joins against advisories filed for example-sdk.

Definition

Vulnerability and currency verdicts are computed externally by joining declared identity against advisory databases; a wheel that misdeclares identity or sources silently breaks that join. This check verifies: identity.purl name+version exactly match METADATA.

When it fires

  • the purl name does not equal the PEP 503 normalization of METADATA Name (re.sub(r'[-_.]+', '-', name).lower())
  • the purl @version does not equal METADATA Version exactly
  • the purl lacks an @version component, or fails the pkg:pypi/... pattern of lifecycle-v1.json
  • the purl type is not pkg:pypi for a wheel distributed through a Python index (type/channel mismatch)

How to fix it

Generate the purl from the same source as METADATA at build time.

  1. Generate the purl at build time from the same variables that populate METADATA: f"pkg:pypi/{normalized_name}@{version}" with the name normalized per PEP 503
  2. Assert purl name and version against the built wheel's METADATA in CI and treat any mismatch as release-blocking
  3. For private packages, keep the standard pkg:pypi type and carry the internal index as a repository_url qualifier (Lifecycle §5.1) rather than inventing a private purl type
