MIRI-PY-034 — Grace period

Deprecated interfaces survive ≥2 releases before removal

should severity MINOR · 2 weight 2 conditional requires previous-release PEP 387Lifecycle §6.1

Definition: standards/python/checks/MIRI-PY-034.yaml · view · raw

Violation
2.0.0: legacy_connect() gains @deprecated and a deprecations entry 2.1.0: legacy_connect() deleted # consumers pinned to 2.0.x never see a release in which the warning exists but the interface still works
Compliant
1.8.0: legacy_connect() gains @deprecated ("use connect(); removal in 2.0.0") 1.9.0-1.9.x: interface still present, still warning 2.0.0: removed — two releases of observable warning preceded deletion

Why this matters

PEP 387 fixes the floor this check enforces: a deprecation warning must appear in at least two minor versions before the interface may be removed, with a five-year window preferred. The floor exists because consumers synchronize on release cadence — a pinned dependency, a regenerated agent skill, a rebuilt CI image each observe one release at a time, so a deprecate-in-N, remove-in-N+1 window means the first signal many consumers ever see is the breakage itself. NumPy's removal of the np.float aliases (warned from 1.20, removed in 1.24) still produced mass downstream AttributeError failures despite a four-release window — evidence that two releases is a minimum, not a target.

Definition

Agents working from frozen model weights cannot read changelogs; deprecation must be marked in code, inventoried in metadata, and never resolved by silent removal. This check verifies: Deprecated interfaces survive ≥2 releases before removal.

When it fires

  • Comparing against the previous release (requirement: previous-release): a public interface absent from the current sdk-manifest.json first appeared in a deprecations inventory only one release before its removal
  • A new deprecations entry declares a removal_version that is the release immediately following the one introducing the deprecation

How to fix it

Keep deprecated interfaces working for at least two releases (PEP 387 shape).

  1. Keep the deprecated interface working, and warning, for at least two releases before deleting it (PEP 387 shape; Lifecycle §6.1)
  2. Set removal_version at deprecation time to at least two minor versions ahead; when plans change, lengthen the window rather than shorten it
  3. If an early removal already shipped, restore the interface in a patch release with the deprecation intact and reschedule the removal
