MIRI-PY-022 — Private-source rule

distribution: private does not rely solely on public OSV

must severity HIGH · 4 weight 3 Lifecycle §5.1

Definition: standards/python/checks/MIRI-PY-022.yaml · view · raw

Violation
lifecycle.json: "identity": {"purl": "pkg:pypi/example-internal@3.2.0?repository_url=https://pypi.internal.example/simple/", "distribution": "private", ...}, "advisory_sources": [ {"type": "osv", "ecosystem": "PyPI", "url": "https://api.osv.dev/v1/query", "authoritative": true} ] # api.osv.dev has never heard of example-internal; every query returns {} — read as 'not vulnerable'
Compliant
"advisory_sources": [ {"type": "osv-internal", "url": "https://osv.internal.example/v1/query", "authoritative": true}, {"type": "osv", "ecosystem": "PyPI", "url": "https://api.osv.dev/v1/query", "authoritative": false} ]

Why this matters

OSV.dev answers /v1/query with an empty object both for a package with no known vulnerabilities and for a package it has never heard of — for a name that exists only on an internal index, the public endpoint therefore returns a clean result unconditionally, forever. A private package whose only authoritative source is public OSV has disabled its own vulnerability signal while passing every scan; the 2021 dependency-confusion research (Birsan) additionally showed that routing internal package names through public infrastructure discloses them to squatters. §5.1 therefore forbids treating public OSV as authoritative for distribution: private packages.

Definition

Vulnerability and currency verdicts are computed externally by joining declared identity against advisory databases; a wheel that misdeclares identity or sources silently breaks that join. This check verifies: distribution: private does not rely solely on public OSV.

When it fires

  • identity.distribution is private and every advisory_sources entry marked authoritative: true is type: osv pointing at the public OSV endpoint
  • identity.distribution is private and no osv-internal or osv-local source is declared at all

How to fix it

Add the internal OSV endpoint as the authoritative source for private packages.

  1. Stand up (or front an existing SCA platform with) an OSV-schema query endpoint serving organization-local records (e.g. IDs like ACME-2026-0001), and declare it as {"type": "osv-internal", ..., "authoritative": true} (§5.2 option 1)
  2. For air-gapped environments, maintain an offline OSV archive in the per-ecosystem all.zip layout and declare it as type: osv-local (§5.2 option 2)
  3. Keep public OSV listed with authoritative: false so the open-source dependency tree remains covered
