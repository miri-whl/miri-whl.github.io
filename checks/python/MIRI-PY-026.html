MIRI-PY-026 — VEX well-formed

vex URL, if present, serves an OpenVEX/CycloneDX VEX document

should severity LOW · 1 weight 1 requires network OpenVEX

Definition: standards/python/checks/MIRI-PY-026.yaml · view · raw

Violation
lifecycle.json: "vex": "https://acme.example/security/vex/latest.json" $ curl -s -o /dev/null -w '%{http_code}' https://acme.example/security/vex/latest.json 404
Compliant
"vex": "https://acme.example/security/vex/example-internal-3.2.0.openvex.json" # serves: {"@context": "https://openvex.dev/ns/v0.2.0", # "statements": [{"vulnerability": {"name": "CVE-2026-1234"}, # "status": "not_affected", "justification": "vulnerable_code_not_present"}]}

Why this matters

VEX is the only standardized vendor-authored exploitability statement — an OpenVEX document carries per-vulnerability status (not_affected, affected, fixed, under_investigation) that consumers use to suppress false positives with an auditable record instead of an ignore-list (§5.4). A declared vex URL that serves nothing is worse than none: a consumer that planned to apply suppressions on its authority either fails the fetch and re-raises every finding, or retries and fails open. A pointer field, once set, must point at a live document.

Definition

Vulnerability and currency verdicts are computed externally by joining declared identity against advisory databases; a wheel that misdeclares identity or sources silently breaks that join. This check verifies: vex URL, if present, serves an OpenVEX/CycloneDX VEX document.

When it fires

  • vex is non-null and fetching the URL returns a non-2xx status
  • The URL resolves but the body parses as neither an OpenVEX document (@context of https://openvex.dev/ns/...) nor a CycloneDX document containing a vulnerabilities[] analysis

How to fix it

Fix or remove the VEX URL; if present it must serve an OpenVEX/CycloneDX VEX document.

  1. If no VEX document exists yet, set vex to null — absence is a valid state; a dead pointer is not
  2. Serve the document from a stable, versioned location and validate it with vexctl (OpenVEX) or CycloneDX schema validation before publishing
  3. Regenerate lifecycle.json so the field tracks the served location
