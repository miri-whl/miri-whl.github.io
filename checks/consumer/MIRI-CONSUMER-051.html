MIRI-CONSUMER-051 — Trigger behavior is independent of what the publisher ships

No shipped field determines whether, when, or how loudly a trigger fires

must severity HIGH · 4 weight 4 conditional Agent Integration Contract §4Consumption Map §3

Definition: standards/consumption/checks/MIRI-CONSUMER-051.yaml · view · raw

Violation
the same dependency.add fires differently for adversarial than for miri
Compliant
identical trigger behavior across byte-identical fixtures; only the findings differ

Why this matters

Every item in the Agent Metadata threat model concerns what the metadata SAYS. This is the first concerning what the metadata MAKES HAPPEN. A package that can force or amplify a trigger has a denial-of-context channel: it consumes the agent's attention on demand, and no existing rule closes it. Content and control are different axes, and a threat model covering only the first keeps being surprised by the second.

Definition

Consumer obligation from Agent Integration Contract 4.3. Conditional: it applies only to a consumer that implements an integration binding.

When it fires

  • Driven with the same trigger against the adversarial and miri fixtures, the consumer emits a response for one arm and NO RESPONSE AT ALL for the other. A trigger that read and found nothing owes the absent envelope of Agent Integration Contract 4.1 — ok true, present false, and a reason — so silence means it never read, and the only thing that could have summoned it is a shipped field. Every .py is byte-identical across the variants, so nothing else can explain the difference. NOTE that findings on the adversarial arm and the ABSENT ENVELOPE on the conforming arm is CORRECT and MUST NOT fire this check; that is the function. An earlier wording fired on "it fires for one and not the other", which made this check fire on the behavior the E3 golden mandates — it treated the outcome of the read as the decision to read.
  • The consumer reads any shipped field to decide whether a trigger fires
  • The consumer reads any shipped field to decide the level or prominence of a finding

How to fix it

Derive trigger behavior solely from the observable event and the consumer's own configuration

  1. Derive trigger behavior solely from the observable event and the consumer's own configuration
  2. Let shipped metadata determine a finding's CONTENT and whether there is anything to report; never let it determine whether the read happens, or a finding's level
